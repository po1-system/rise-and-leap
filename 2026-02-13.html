Executive Summary

今回の要点

AIの性能より先に、比較・判断できるデータ構造が成果を決める。

和雄さんの案件分析では、求人情報を大量に保存していても、一案件一タブの形式では比較・分析できず、AIの判断精度も上がらないことが判明した。一行一案件のデータベースへ改め、会社情報やコンテンツの利用目的まで含めて整理する方針が決定。健太郎さんのAppSheet開発でも、画面より裏側のデータ構造、更新監視、重要情報の抽出、管理者向けアラートが重視された。情報収集、構造化、人間の理解、AI分析、仮説、行動という順序が示され、研究会はAI設計から情報設計の段階へ進んだ。

Discussion

主な議論

応募の失敗分析から、データ信頼性と統合業務システムへ広がった33の論点。

Result

受注ゼロから方法を疑う

行動量は確保しても不採用、枠終了、返信なし。同じ方法で件数だけ増やさず、原因と次の行動を見直す。

Gem

分析用Gemを実践する

経歴と一週間の行動から現状、課題、ボトルネックを整理。ただし本人の分析とAIの推測を分けて検証する。

Positioning

学習者として戦う限界

学習が成果へ変わらず、管理経験、WordPress、GAS、AI、PM志向が一本の専門性として伝わっていない。

Perspective

内面と相手の需要を分ける

本人の強みがあっても、応募先が求めていなければ評価されない。提案文より案件選択の問題を疑う。

Role

執筆とディレクションを分ける

ライターには正確さと専門性、管理経験はメディア立上げ、編集、進行、マニュアル、企画で生かす。

Portfolio

学習を業務改善実績へ

WordPress、Sheets、GASを連携し、入稿できるだけでなく制作・入稿・管理を効率化する成果へ変える。

Proposal

提案文を本人の言葉へ

応募理由、経験との接点、解決できる課題、学び、貢献を自分の言葉で示し、機械的な文章から脱する。

Scope

応募案件の属性を広げる

執筆に限定せず、ディレクション、進行管理、マニュアル、コンテンツ管理、調査、運営補助も探す。

Feedback

短い周期で相談する

一人で一週間進めず、案件選択や応募文を途中共有し、AI分析や判断のズレを早く修正する。

Understanding

保存と理解を分ける

AIへ保管しても、人間が内容を思い出し、比較し、判断できなければ学びや分析にはならない。

Database

一案件一シートをやめる

縦長の全文コピーはドキュメントの収納。一行一案件・一列一項目で一覧、絞込、集計を可能にする。

Analysis

収納を意思決定へ変える

条件、会社、目的、結果、評価を同じ基準で横並びにし、傾向や不足を比較できる状態へ変える。

Context

会社と利用目的を記録

自社メディア、広告、受託、SEO、採用広報など、同じ執筆でも異なる発注背景と必要能力を把握する。

Density

一画面で比較できる密度

会社、業種、業務、報酬、条件、適合度、応募日、結果、URLを並べ、複数案件を同時に見渡す。

Human Design

AIは悪い構造を直さない

AIが回答しても、保存方法、欠損項目、比較可能性、目的適合が正しいとは限らない。人間が設計する。

PDCA

正しいデータからPlanを作る

情報、比較構造、人間の分析、AI補助、仮説、計画の順を守り、推測を起点とするPDCAを避ける。

Channel

媒体評価も整理の後

媒体、提案、経歴、実績、案件種別、募集速度を分け、どの要因が結果へ影響したかを比較する。

Practice

実務に触れて仕事を知る

未経験可で受かりやすい案件も経験し、外側からの分析だけでは得られない品質、報酬、適性を学ぶ。

Manual

実装しながら手順を育てる

Geminiの古い情報や誤りを実操作と照合し、AppSheetマニュアルと操作知識を同時に更新する。

Repeat

作り直して速度を測る

同じ在庫管理アプリを再構築し、手順の定着、マニュアル改善、開発時間、エラー対応力を比較する。

Stock

アプリと機能を蓄積する

日報、顧客、タスクなど異なるアプリで、データ構造、画面、連携の再利用可能な選択肢を増やす。

Input Base

AppSheetを入力基盤にする

正しく構造化した情報の入口として使い、AI、Looker Studio、GAS、他システムへつなげる。

Tool Roles

目的ごとにツールを分ける

入力はAppSheet、可視化はLooker Studio、自然言語確認はAI、自動処理はGASが担う。

Text Data

重要な文字情報も管理

事故、破損、要望、課題、対応事項を分類・抽出し、数値ダッシュボードで見えない問題を表示する。

Priority

入力時に重要度を持たせる

緊急、重要、通常、経過観察を選び、表示、通知、期限監視、AI要約の対象を安定させる。

Decision UI

次の判断を促す画面

数値の状態だけでなく、放置問題、面談対象、期限超過、継続課題を管理者へ思い出させる。

Completeness

入力されるべき情報を監視

未入力、未更新、未確認を検知し、色、一覧、ダッシュボード、本人通知で管理作業を減らす。

Trust

データの信頼性を管理

情報が最新・完全・正確かを監視し、更新漏れによる誤判断とシステムへの不信を防ぐ。

Behavior

人の行動まで支援する

入力、対応、更新、放置、停滞を捉え、通知、リマインド、エスカレーションを自動化する。

Platform

個別から統合アプリへ

在庫、日報、顧客、タスク、アラート、経営情報を一つの入口から扱う業務基盤を構想する。

Roles

入力者と管理者のUIを分ける

現場には少ない項目とスマホ操作、管理者には全体、問題、未入力、判断事項を提示する。

Monitoring

AIの監視条件を定義する

重要度、決定、期限、担当、未完了、キーワード、前回差分を先に設計し、曖昧な監視を避ける。

Trigger

GASを動かす条件を設計

登録、未更新、緊急、期限超過、特定文字、異常値を起点に、通知、集計、転記、AI要約を実行する。

Decisions

決定事項

情報を集めることから、比較・監視・判断できる構造へ。

01

一行一案件へ再構築

個別タブを廃止し、会社、種類、目的、条件、結果、URL、所感を同じ列で管理する。

02

人間の理解を先に置く

過去案件を本人が分類・分析してからAIへ渡し、分析が終わるまで件数だけを増やさない。

03

応募領域と実務経験を広げる

編集、進行、マニュアルなども探し、未経験でも実務を知れる案件へ一定数応募する。

04

学習を説明できる実績へ

WordPressとGASの連携を完成させ、提案文と職務経歴も本人の言葉へ直して途中共有する。

05

データ構造からアプリを作る

異なるAppSheetアプリを作り、実装結果でマニュアルを更新し、裏側の表構造を先に設計する。

06

信頼性を監視する

重要度、更新日、担当、期限を持たせ、未入力・未更新・緊急事項を検知する。

07

管理者の判断を支える

重要な文字情報と対応事項を抽出し、入力者とは異なる管理者向けダッシュボードを設計する。

08

役割分担された業務基盤へ

AppSheet、GAS、Looker Studio、AIを組み合わせ、将来は複数業務を統合する。

前回からの変化

専門AIを作ることから、そのAIが正しく働ける情報世界の設計へ。

2月6日は、日次通知、週次振り返り、長期目標を設計図へまとめ、業務別の専用Gemと用途別の情報によってAI活用を再利用する考えが中心だった。2月13日、和雄さんが分析Gemを実際に作ると、元データの保存形式が比較に適さず、AIの分析精度も上がらないことが判明。一案件一タブから一行一案件へ移行し、会社情報と利用目的を含める方針が決まった。AppSheetでも画面より裏側の構造、更新監視、重要な文字情報、管理者の判断が重視され、AppSheet、GAS、Looker Studio、AIの役割分担が具体化した。

Historical Position

歴史的な位置づけ

AIアーキテクチャから、情報アーキテクチャへ移行した回。

優れたGemやAIを作っても、入力データが整理されていなければ良い結果は出ない。情報量が多く分析結果が生成されても、人間が比較できず、会社や利用目的を理解できず、根拠を説明できないなら意思決定には使えない。AI時代には、何を、どの単位と項目で記録し、誰が見て、どの条件を監視するかという設計が不可欠である。AppSheetの焦点も見た目と個別機能から、データの正確性、更新状況、重要情報、担当者の行動、アラート、自動処理へ移った。後のOpenClawにおけるデータベース、Signals、Projects、Timeline、ExecutionLogs、ApprovalLogs、状態監視、差分検知、承認要求につながる重要な原点である。

Structure before intelligence.AIが正しく判断できる情報世界を、人間が設計する。
